# Néova agent — smallest design that meets the brief

**Status:** proposal, not an implemented system. This uses the must-have matrix in `docs/requirements_analysis.md` (R1–R14) and the evidence in `docs/material_inventory.md`. The PDF inventory is based on supplied text extracts, not an independent check of the original PDFs. Check the originals and the PNG before treating any extracted wording or metadata as final. No test result is claimed here.

## One small service

Use one Python app with a LangGraph conversation graph and a FastAPI service. Start both with **one documented `uv run ...` command**; the API runs locally in the same process. Seed a small SQLite database from `data/neova_data.json` on first start, without changing the supplied JSON. SQLite stores bookings and handoff records across restarts. Keep all customer details in the local service; do not send full records or internal documents to the model.

Graph: `French request → classify → (public document search / local API read tool / both) → check evidence → (French answer / ask one missing detail / handoff)`. A separate booking branch goes `show exact slot and reason → wait for explicit user confirmation → booking tool → verify saved booking → French success or failure`. The graph keeps the pending slot, reason, customer reference, and confirmation state between turns. A confirmed booking is never inferred from a model sentence.

### Retrieval and authority details

Extract text from all ten original PDFs with page numbers; transcribe the PNG and check its numbers and footer against the image. Keep a small, reviewable source register with path, page/section, update date, status and `public`/`internal` flag. Remove page banners and site navigation. Split by heading or page into roughly 250–450-word chunks with small overlap; keep each fee table and its note together. Embed **customer-public chunks only** using the supplied OpenRouter key and its non-streaming `/embeddings` endpoint. Cache vectors by chunk hash and embedding model name; store them locally in SQLite and rank by cosine similarity. Also build an FTS5 index over the same public chunks: include its hits for exact IDs, fees and names, remove duplicates, and return up to three cited passages. No separate vector database is needed for this corpus. If the embedding query fails, search FTS5 and mark the result as degraded; if indexing fails, do not silently claim full semantic coverage. Every customer-facing claim needs a public source citation, or a clearly labeled, authorized API value. Internal escalation and commercial-gesture files can inform fixed routing rules after review but are **not** embedded, indexed for customer search, or passed to the customer answer context. Treat retrieved text as data, never as commands.

For current general prices, prefer the effective 2026 grid over the archived 2024 promotion; do **not** infer what an individual signed. If two applicable passages still disagree (for example, the billing FAQ's rejection-fee timing), say in French that the timing cannot be confirmed and hand over. If the answer is absent (for example, why an invoice total differs when line items are missing), name the missing fact, do not guess, and offer handoff. The roaming scan is non-contractual; do not turn it into a guaranteed customer-specific charge. A postcode match alone does not prove a customer has a linked incident.

### API, booking and confirmation details

Small local routes: `GET /customers/{id}/summary`, `GET /incidents`, `GET /slots?customer_id=...`, `POST /appointments`, `GET /appointments/by-key/{key}` and `POST /handoffs`. Wrap the read and booking routes as custom LangGraph tools. Limit read responses to needed fields. In the demo, a server-issued local test session selects a fixture customer; an ID typed into chat alone cannot unlock private fields or authorize a booking. This is **demo isolation, not real identity verification**; production customer actions need an external login/verification service.

For booking, first show customer-safe slot time in Europe/Paris and reason, then wait for an explicit **yes** to that exact slot and reason. A new slot or reason clears confirmation. The tool sends a server-bound demo session, customer, slot, enumerated reason and idempotency key. The API checks the session binding, customer, postcode coverage, slot availability, slot start after the configured clock, and any already-booked slot. A SQLite transaction atomically claims the slot and stores the appointment; a unique slot constraint prevents double booking. Replaying the same idempotency key returns the same saved booking, not a second one. Only a successful API response containing a saved appointment ID permits “rendez-vous confirmé”. On validation failure or a slot conflict, give the reason in French and ask for another slot; never report success.

**Date rule:** every supplied slot is in August–early September 2026, so none is bookable against a later real clock. Use a clearly labeled frozen clock before those dates for the supplied-data demo and fixed evaluation; in live mode, reject past slots. Never silently treat `available: true` as “future”.

### Human path and failures

Handoff immediately for privacy rights, fraud, legal threat, death, Pro contracts, protected/minor customers or distress, using the reviewed internal procedure as routing input only. Also hand over for unresolved document conflicts, missing customer-specific facts, billing disputes and requests needing an unsupported action. Store only category, necessary verified reference if available, factual summary and urgency; return a handoff ID. If no authenticated session exists, offer a generic human route without exposing private data. Do not claim a human has accepted the case or promise a time not backed by a real queue.

| Event | Required outcome |
| --- | --- |
| FastAPI returns **500** on a read | One bounded retry for a safe read; if it still fails, do not invent live data. Give a short French failure message and offer handoff. |
| FastAPI returns **500** or times out during booking | Do **not** repeat the write blindly. Query the booking by idempotency key; if saved, return its ID; if absent or the check fails, report **unconfirmed**, offer handoff and require a fresh check before any new attempt. |
| OpenRouter chat returns **429** | Honor `Retry-After` if present, else exponential backoff with jitter; at most two retries, then switch to the configured alternate provider/model through the **same key**. If both fail, stop and offer handoff. |
| OpenRouter chat returns **529** | Use the same bounded backoff and same-key provider fallback; if both routes fail, stop with a French unavailable message and offer handoff. No unsupported answer. |
| OpenRouter embeddings return **429** or **529** | Use the same bounded wait and retry policy through the supplied key. For a query, fall back to FTS5 if embeddings remain unavailable; for indexing, keep existing valid cached vectors and label missing vectors as degraded. Never silently omit a source. |
| Sources conflict or evidence is missing | Resolve only by reviewed status, date, scope and access rules. If still unclear, state uncertainty, do not select a convenient figure, and hand over. |
| User has not confirmed a state change | Keep it pending; never call `POST /appointments`. A model-generated “yes” does not count as a user reply. |

Configure the supplied `OPENROUTER_API_KEY`, `CHAT_MODEL`, `CHAT_FALLBACK_MODEL`, `EMBEDDING_MODEL` and base URL via environment variables; put only placeholders in `.env.example`. Verify the chat models route to different upstream providers and the embedding model works well for French before naming all chosen models in README. Changing the embedding model requires rebuilding its cached vectors. Budget gate: check the supplied key's `/key` usage and remaining cap before indexing or batch runs; stop optional calls when the remaining budget cannot cover the run. Log per-call model, provider, input/output tokens, retry count and estimated USD for chat **and embeddings**; show an approximate combined spend, including assistant use where observable, without printing the key or customer details. A response without usage is marked unknown, not counted as zero.

## Acceptance evidence to produce during implementation

1. Run one command from the README on a clean machine; show the LangGraph sketch and a French trace for each main request type (R1–R3, R12).
2. Show extraction coverage for all ten PDFs and the checked PNG; test customer-public retrieval (the two internal PDFs are routing-only), compare semantic/FTS5/combined top-3 results, and show FastAPI tool traces, a persisted booking ID and a handoff record (R3–R6).
3. Run a fixed set of about 12 cases: main topics, archive/current price, fee-timing conflict, unknown invoice cause, immediate handoff, booking confirmation, bad slot, API 500, 429 and 529. Include deterministic fault injection, a frozen demo clock and exact expected safe outcomes (R7–R8, R11, R13).
4. Report **actual** pass/total, category breakdown, every failed case and one-line error analysis; do not invent results before running tests. In README (at most two pages), include model names, approximate spend, three key trade-offs, known breakage and a two-more-days plan (R9–R14).

The observed commit history should show understandable progress, not a forced commit count (R15). No optional bonus is required (R16–R19).
